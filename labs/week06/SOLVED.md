## 2. Μοντέλα ελέγχου

### 2.1 Διαμέριση ισοδυναμίας

| Είσοδος | Έγκυρες κλάσεις | Άκυρες κλάσεις |
|---|---|---|
| Ώρα παραγγελίας (FR-08) | EC1: 00:00:00–16:59:59, χωρίς έκπτωση · EC2: 17:00:00–18:59:59, έκπτωση 20% · EC3: 19:00:00–23:59:59, χωρίς έκπτωση | — |
| Κουπόνι (FR-06), για υποσύνολο 10,00 € | EC4: κουπόνι 0 · EC5: κουπόνι > 0, το ποσό μειώνεται αλλά όχι κάτω από 0 | EC6: κουπόνι < 0 |

Η ώρα δεν έχει άκυρη κλάση: κάθε στιγμή της ημέρας είναι έγκυρη είσοδος. Το EC1 και το EC3 έχουν την ίδια έξοδο, αλλά είναι χωριστές κλάσεις γιατί βρίσκονται σε διαφορετική πλευρά του EC2 και έχουν διαφορετικά όρια.

Για να ελέγχει ένα test μόνο τη FR-08, το υποσύνολο είναι 20,00 €: μέσα στο happy hour το ποσό γίνεται 16,00 €, έξω μένει 20,00 €, και στις δύο περιπτώσεις πάνω από το όριο δωρεάν αποστολής. Με υποσύνολο 18,00 € το happy hour θα έδινε 14,40 € και θα άλλαζε και η αποστολή: το test θα έλεγχε δύο απαιτήσεις μαζί.

### 2.2 Ανάλυση οριακών τιμών

Ανάλυση 3 τιμών, γιατί οι FR-03 και FR-08 είναι κανόνες χρέωσης με κίνδυνο υψηλής προτεραιότητας (R-01, R-02).

| Είσοδος | Όριο | Τιμές ελέγχου (κάτω / πάνω στο όριο / πάνω) | Αναμενόμενη συμπεριφορά |
|---|---|---|---|
| Ώρα (FR-08) | B1: 17:00:00 | 16:59:59 / 17:00:00 / 17:00:01 | Χωρίς έκπτωση / έκπτωση / έκπτωση |
| Ώρα (FR-08) | B2: 19:00:00 | 18:59:59 / 19:00:00 / 19:00:01 | Έκπτωση / χωρίς έκπτωση / χωρίς έκπτωση |
| Ποσό μετά τις εκπτώσεις (FR-03) | B3: 15,00 € | 14,99 / 15,00 / 15,01 | Αποστολή 2,00 / 0,00 / 0,00 |
| Ποσό μετά τις εκπτώσεις (FR-03), ως έξοδος του happy hour | B3΄: 15,00 € | υποσύνολο 18,75 € στις 18:00 | 18,75 × 0,8 = 15,00 → αποστολή 0,00 |
| Κουπόνι (FR-06) | B4: 0 | −0,01 / 0 | Απόρριψη / ποσό αμετάβλητο |
| Κουπόνι (FR-06) | B5: = υποσύνολο | 10,00 / 10,01 | Ποσό 0,00 / ποσό 0,00 (όχι αρνητικό) |

Το B3΄ είναι όριο της **εξόδου** του happy hour, που γίνεται είσοδος της FR-03. Ελέγχει ότι η αποστολή υπολογίζεται στο ποσό μετά τις εκπτώσεις, όπως λέει η απαίτηση.

Επιπλέον, με εικασία σφάλματος (29119-4, 5.4.1): η ώρα 19:59:59. Αν η υλοποίηση συγκρίνει μόνο την ώρα και όχι τα λεπτά, εδώ θα φανεί.

### 2.3 Πίνακας αποφάσεων

Η ολοκλήρωση παραγγελίας, όπως στη διάλεξη, συμπτυγμένη:

| Συνθήκες / Κανόνες | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| Καλάθι μη κενό (FR-02) | Α | Α | Α | Ψ |
| Εστιατόριο ανοιχτό (FR-07) | Α | Α | Ψ | – |
| Η πληρωμή εγκρίνεται | Α | Ψ | – | – |
| **Ενέργειες** | | | | |
| Παραγγελία σε «υποβλήθηκε», άδειασμα καλαθιού | ✓ | | | |
| Απόρριψη με αιτία, καλάθι ως είχε (FR-10) | | ✓ | | |
| «Εκτός ωραρίου», καμία χρέωση | | | ✓ | |
| «Κενό καλάθι» | | | | ✓ |
| **Πλήρεις συνδυασμοί** | 1 | 1 | 2 | 4 |

Άθροισμα 1 + 1 + 2 + 4 = 8 = 2³. Η σύμπτυξη του R4 υποθέτει ότι το κενό καλάθι ελέγχεται πρώτο. Οι FR-02 και FR-07 δεν ορίζουν προτεραιότητα· η ερώτηση στάλθηκε στην επιχείρηση και η υπόθεση καταγράφεται ως παραδοχή. Για τις παύλες του R4 επιλέχθηκαν ανοιχτό εστιατόριο και κάρτα που εγκρίνεται, ώστε η μόνη αιτία απόρριψης να είναι το καλάθι.

Το εστιατόριο αντικαθίσταται στο όριο του `CheckoutService` με αντικείμενο που επιστρέφει `is_open()` αληθές ή ψευδές. Ο έλεγχος του ίδιου του ωραρίου (11:00–23:30) **δεν** γίνεται, γιατί το `Restaurant.is_open` διαβάζει το ρολόι του συστήματος και δεν δέχεται στιγμή (Ενότητα 6).

| TC-BB-35 | Η ακύρωση έγινε δεκτή, κατάσταση «ακυρώθηκε», επιστροφή χρημάτων | Fail | Κώδικας | INC-03 |
| Τα υπόλοιπα 47 | Όπως αναμενόταν | Pass | — | — |

Και τα έξι Fail ταξινομούνται ως ελαττώματα κώδικα: η απαίτηση είναι σαφής, το test ελέγχει μόνο αυτή, και το αναμενόμενο αποτέλεσμα προκύπτει άμεσα από το κείμενό της. Αν η απαίτηση ήταν «έως τις 19:00», το TC-BB-07 θα ταξινομούνταν ως ασάφεια της απαίτησης και θα γινόταν ερώτηση.

**INC-01 · Η έκπτωση happy hour ισχύει έως τις 19:59:59.** Βήματα: καλάθι 20,00 €, χωρίς κουπόνι, `total` με now 2/11/2026 19:00:00. Αναμενόμενο 20,00 € (FR-08: έως 18:59:59). Πραγματικό 16,00 €. Το ίδιο για 19:00:01 και 19:59:59· στις 20:00:00 και μετά, σωστά. Σοβαρότητα: υψηλή, λάθος χρέωση για μία ώρα κάθε ημέρα. Το TC-BB-09, από την εικασία σφάλματος, υποδηλώνει ότι η υλοποίηση συγκρίνει μόνο την ώρα και όχι τα λεπτά.

**INC-02 · Χρέωση αποστολής 2,00 € για ποσό ακριβώς 15,00 €.** Βήματα: καλάθι 15,00 €, χωρίς κουπόνι, now 12:00. Αναμενόμενο 15,00 € (FR-03: τουλάχιστον 15,00 €). Πραγματικό 17,00 €. Το ίδιο όταν τα 15,00 € προκύπτουν μετά το happy hour (TC-BB-14). Σοβαρότητα: μέση, λάθος χρέωση σε ένα μόνο ποσό, αλλά σε ποσό που οι πελάτες στοχεύουν σκόπιμα.

**INC-03 · Ο πελάτης ακυρώνει παραγγελία που έχει γίνει αποδεκτή.** Βήματα: παραγγελία σε «υποβλήθηκε», αποδοχή, ακύρωση από τον πελάτη. Αναμενόμενο: απόρριψη χωρίς αλλαγή κατάστασης (FR-11). Πραγματικό: κατάσταση «ακυρώθηκε» και επιστροφή όλου του ποσού. Σοβαρότητα: υψηλή, το εστιατόριο έχει ήδη δεσμευτεί και χάνει τα χρήματα (R-03). Σημείωση για την ομάδα ανάπτυξης: η διόρθωση πρέπει να ελεγχθεί και στον πίνακα των επιτρεπτών μεταβάσεων και στη συνάρτηση ακύρωσης· το TC-BB-35 περνά μόνο αν διορθωθούν και τα δύο.

Ο κώδικας δεν διορθώθηκε. Οι αναφορές καταχωρίζονται ως νέοι ή αναθεωρημένοι κίνδυνοι στο `risks.md`: η πιθανότητα των R-01, R-02 και R-03 γίνεται «υψηλή», αφού το ελάττωμα επιβεβαιώθηκε.

Κάλυψη απαιτήσεων: 8 από τις 13 λειτουργικές απαιτήσεις έχουν τουλάχιστον ένα black-box test. Δεν ελέγχθηκαν:

- FR-01, FR-05: καλύπτονται από τα starter tests, χωρίς οριακές τιμές. Προγραμματίζονται για την Εβδομάδα 8.
- FR-04: δεν υλοποιείται στην έκδοση 0.1 (Εβδομάδα 2).
- FR-09 (στρογγυλοποίηση): κανένα test δεν φτάνει σε ποσό με τρίτο δεκαδικό. Κενό που πρέπει να καλυφθεί.
- FR-12: χρειάζεται πύλη που αποτυγχάνει στην επιστροφή χρημάτων· Εβδομάδα 9.
- Το ωράριο του εστιατορίου (FR-07) ελέγχθηκε μόνο ως συνθήκη του πίνακα αποφάσεων. Το `Restaurant.is_open` δεν δέχεται στιγμή, οπότε τα όρια 11:00 και 23:30 δεν ελέγχονται χωρίς αλλαγή του ρολογιού. Είναι ακριβώς ο κίνδυνος ελεγξιμότητας R-07 (NFR-04).

Δεν ελέγχθηκε επίσης ποιο μήνυμα δίνεται όταν το καλάθι είναι κενό **και** το εστιατόριο κλειστό, γιατί οι απαιτήσεις δεν ορίζουν προτεραιότητα (Ενότητα 2.3).

## 7. Σύγκριση με την Εβδομάδα 5

Κανένα από τα τρία ελαττώματα δεν είχε εντοπιστεί πριν. Το ruff και το radon δεν τα βλέπουν: ο κώδικας είναι συντακτικά σωστός και απλός, βαθμίδας A. Το review του PR #12 στην Εβδομάδα 5 εξέταζε τις αλλαγές του `checkout.py` και του `pricing.py`, όχι το `orders.py`. Τα INC-01 και INC-02 βρίσκονταν σε γραμμές του `pricing.py` που το PR δεν άλλαζε, άρα έξω από το αντικείμενο της inspection. Ένας reviewer με τη FR-08 μπροστά του θα μπορούσε να δει το `<= 19`· χωρίς αυτήν, η γραμμή μοιάζει σωστή. Τα όρια και οι μη έγκυρες μεταβάσεις βρίσκονται συστηματικά μόνο με τεχνικές που ξεκινούν από την απαίτηση.
